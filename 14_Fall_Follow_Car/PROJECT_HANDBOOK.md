## 一、專題一句話

用**樹莓派 5**當大腦，結合**相機視覺（YOLOv8-pose）**與**UWB 距離感測**，讓小車能「跟著人走」；同一套骨架辨識再做**跌倒／異常姿態偵測**，確認後透過 **LINE** 推播文字、照片與短片，並**立刻緊急煞停馬達**，形成「陪伴跟隨 + 安全通報」一體的原型系統。

## 二、為什麼做這個？（核心理念與意義）

### 2.1 問題意識

高齡照護、居家陪伴常見兩類需求：

1. **移動陪伴**：照顧者／被照顧者移動時，載物或輔助裝置最好能「自動跟上去」，減少反覆回頭叫車、推車。
2. **跌倒風險**：跌倒是高齡常見傷害來源；若無人在旁，黃金通報時間容易錯過。

傳統方案常把「跟隨」與「跌倒偵測」拆成兩套設備：跟隨用感測器／遙控，跌倒用穿戴或固定監視器。本專題刻意用**同一相機 + 同一邊緣運算平台**把兩者合在一起，讓小車同時具備「跟著你」與「倒了會叫人」的能力。

### 2.2 設計理念（四個核心）

| 理念 | 意義 | 在系統中的體現 |
|------|------|----------------|
| **邊緣運算優先** | 影像與控制在本地完成，不依賴雲端即時推流也能動 | Pi 上跑 YOLO + 控制迴圈；雲端只用在 LINE 媒體上傳 |
| **感測分工、決策融合** | 視覺擅方向、UWB 擅距離，各做各擅長的事 | 畫面左右 → 轉向；UWB 公尺距離 → 前進／停 |
| **寧可慢確認、不可亂報** | 跌倒通報誤報成本高（嚇到家屬、干擾照顧） | 約 10 秒確認窗；桌前坐姿明確排除；中途站起則刪暫存 |
| **安全優先於跟隨** | 確認跌倒時，繼續跟著人走是危險的 | 確認後送緊急煞停 `X`，可自動關閉跟隨 |

### 2.3 專題價值（可寫進報告的「貢獻」）

1. **系統整合價值**：把原本分散的跌倒模組（`12_`）與跟隨模組（`13_`）收斂成一支可部署的 Flask 服務（`14_`）。
2. **工程可行性**：針對樹莓派 5 實際串列陷阱（debug UART 不是可靠馬達口），改採「ESP32 USB 雙向：讀距離 + 轉發馬達命令」的務實架構。
3. **通報可靠度**：LINE 只接受公開 HTTPS 媒體；系統做多層圖床／隧道備援，提高真實環境下「有圖有影」的成功率。
4. **姿態語意改良**：不只「躺平才算倒」，而以可調靈敏度涵蓋蹲下／半倒，同時排除桌前打字坐姿，貼近真實居家情境。

### 2.4 明確不做／尚未做的事（避免報告過度宣稱）

- **暫不含 MaUWB AOA**（角度／定位融合尚未接入；目前方向靠相機，距離靠 DS-TWR 類 UWB）。
- **非醫療級跌倒診斷**：屬原型／展示系統，不宣稱取代穿戴式醫療警報或護理站設備。
- **VL53 近距避障已停用**（2026-11-25）；尚無下視防墜／AOA。舊 4×VL53 接線見 `DEPLOY.md` 附錄。
- 馬達驅動器（如 BMP73T104）有硬體過流保護（OCP）；劇烈原地轉向仍可能觸發，屬硬體限制，需用軟體弧線轉向與機構調校緩解。

## 四、功能說明（給使用者看的行為）

### 4.1 網頁操作模型

1. 啟動後預設**僅預覽**（不驅動馬達、不發 LINE）。
2. 網頁可**分別**開關：
   - **跟隨**：才會送 `F/L/R/Z` 等運動命令。
   - **跌倒偵測**：才會累計疑似秒數並在確認後通報。
3. 瀏覽器看即時 MJPEG 骨架／框線預覽（預設 `http://樹莓派IP:5001`）。

意義：開發與展示時可「先看骨架不開車」「先開車不報警」，降低調試風險。

### 4.2 視覺跟隨行為表

| 條件 | 馬達命令 | 意義 |
|------|----------|------|
| 跟隨關閉 | `S` | 預覽安全 |
| 畫面沒人 | `Z` | 自轉搜尋目標 |
| 人在畫面左側（超出死區） | `L` | 先對準再前進 |
| 人在畫面右側 | `R` | 同上 |
| 置中且距離 ≥ 2.0 m | `F` | 跟上 |
| 置中且距離 < 1.8 m | `S` | 保持社交／安全距離 |
| 置中且 1.8～2.0 m | 維持上一 F 或 S | 緩衝帶，避免門檻抖動 |
| 置中但 UWB 過舊／失效 | `S` | 沒有可靠距離就不前進 |
| **確認跌倒** | **`X`** | **緊急煞停**（優先於跟隨） |

### 4.3 跌倒偵測行為表

| 階段 | 行為 | 意義 |
|------|------|------|
| 偵測關閉 | 不計時、不錄事件 | 避免誤報 |
| 姿態疑似跌倒／蹲下／半倒 | 開始計時；建立 pending 事件；寫入循環緩衝前情 | 「可能出事，先錄起來」 |
| 滿約 10 秒仍異常 | **確認跌倒**：媒體移到 confirmed、推 LINE、馬達 `X`、可關跟隨 | 真警報 |
| 10 秒內站起／坐回／失去人體／手動關閉偵測 | 丟棄 pending、刪暫存 | 假警報自清 |
| 警報冷卻（約 30 秒） | 避免連續狂傳 LINE | 保護通道與使用者體驗 |

### 4.4 通報內容（LINE）

確認跌倒後典型推播包含：

- **文字**：緊急安全通報 + 側向／正面類型 + 時間戳
- **照片**：當下畫面（常經 ImgBB 等取得 HTTPS URL）
- **影片**：含跌倒前循環緩衝的短片（多圖床備援）

## 五、技術核心（報告「方法」章節可直接用）

### 5.1 為何用 YOLOv8-pose？

- 輸出人體 **bounding box + 關鍵點**（鼻、肩、腕、髖、膝等 COCO 骨架）。
- 同一模型同時服務：
  - **跟隨**：用人框水平位置算 `offset ∈ [-1, 1]`（左負右正）。
  - **跌倒**：用關鍵點幾何關係判斷「是否異常姿態」。
- 在樹莓派上選 `yolov8n-pose`（nano）是速度與精度折衷；`YOLO_IMGSZ` 預設 320 降負載。

### 5.2 跟隨決策：視覺管方向、UWB 管距離

**核心理念**：單目相機估真實公尺距離不穩；UWB DS-TWR 類測距較適合「該不該前進」。相機則很適合「人偏左還偏右」。

伪流程：

```
讀一幀 → YOLO
  → 有無人？無人則 Z
  → |offset| > 死區？ → L 或 R（先對準）
  → 已置中 → 看 UWB 距離與新鮮度 → F / S / 維持緩衝帶
```

重要工程細節：

- **控制迴圈與 MJPEG 串流分離思維**：決策要穩定，不該被瀏覽器拉流拖慢到「命令斷斷續續」。
- **命令節流**（`CMD_INTERVAL_SECONDS`，約 0.15s）：避免序列埠與馬達被刷爆。
- **UWB stale**：距離超過約 1 秒未更新則不前進，避免「幽靈距離」。

### 5.3 跌倒姿態：可調靈敏度 + 桌前排除

`analyze_pose()` 的設計目標寫在程式註解裡，也是產品語意：

> - 桌前坐姿／低頭打字 → **不報**  
> - 蹲下、半倒、躺平 → 依 `FALL_SENSITIVITY` **可報**（預設偏敏感）

關鍵幾何概念：

- **aspect_ratio**（框寬／高）：側摔常變「扁」
- **torso_height / head_to_hip**：倒地或壓縮姿態時變短
- **shoulder 在畫面中的高度**：人是否整體偏低
- **膝蓋靠近髖**：蹲下特徵
- **桌前坐姿启发式**：手腕接近髖高度、頭仍在腕上方、肩膀仍偏畫面上方 → 判定為操作桌面，直接不報

`FALL_SENSITIVITY`（預設 **1.45**，夾在約 0.8～2.5）：

- 越大 → 門檻越寬 → 越容易進入「疑似」
- 越小 → 越嚴 → 幾乎要更明顯倒地才觸發

這讓展示現場可調「寧願多抓」或「寧願少報」，而不改程式邏輯。

### 5.4 行車紀錄器式循環緩衝

系統持續把最近約 **30 秒**畫面以 JPEG 佇列保留（無跌倒就自動覆蓋）。  
一旦進入疑似跌倒，事件影片可帶**前情**，而不是只從按下警報那一幀開始——對事後釐清「怎麼倒的」很有幫助。

### 5.5 LINE 媒體上傳鏈（可靠性工程）

LINE 官方訊息**不能直接塞本機檔案**，必須是伺服器可抓的 **HTTPS URL**。

**照片**傾向：ImgBB 等 LINE 較吃得下的圖床。  
**影片**上傳順序（整合版）：

1. litterbox（可過期；實務上有時 500）
2. catbox（實務上有時被擋 IP／412）
3. **uguu**（短效自動刪，直連 mp4）
4. **pomf**（備援）
5. **cloudflared `PUBLIC_BASE_URL`**（本機隧道；需網址新鮮）

核心理念：**單一圖床不可靠時，備援鏈比死磕一家重要**；短效自動刪也較符合「通報用途、不必永久存公開網」的隱私取向。

### 5.6 序列埠架構為何長這樣？

實作經驗結論（建議寫進「實作困難與解決」）：

- Pi 5 的 `serial0` / `ttyAMA0` **常不是**接到 UNO 的可靠路徑（debug UART 陷阱）。
- 無額外 USB-TTL 時，採：
  - **車上 ESP32 USB ↔ Pi**：同一口讀 `D:x.xx`、寫馬達字母
  - **ESP32 GPIO17 → UNO D10**，GND 共地，由 ESP32 Serial2 轉發
- 程式若偵測到把馬達口設成 Pi5 陷阱裝置，會自動改走 UWB USB 轉發並警告。

電源安全理念：

- 高電壓電池（如 14.8V 級）只給馬達驅動，**不可灌進 UNO 5V**。
- UNO 建議獨立 5V（行充等），但 **GND 必須與馬達側共地**，否則轉發／通訊不穩或損壞風險上升。
- 硬轉彎可能觸發驅動器 OCP → 需清保護並考慮軟體弧線／較緩和的轉向策略。

## 六、硬體清單與接線（展示用）

### 6.1 建議 BOM（概念）

- 樹莓派 5 + 相機
- 車上：ESP32-UWB（Responder）、Arduino UNO、馬達驅動（例：BMP73T104）、底盤與電池組
- 人身上：ESP32-UWB（Tag／Initiator）
- 網路線／Wi-Fi（網頁預覽與 LINE 上傳）
- （可選）cloudflared 做臨時 HTTPS 隧道

### 6.2 建議接線（與 DEPLOY／FEATURES_PINOUT 一致）

```
人身上 ESP32-UWB (Tag)  --UWB-->  車上 ESP32-UWB (Responder)
                                         │ USB（D: / O: / 馬達命令）
                                         ▼
                                    樹莓派 5 + 相機
                                         │
              GPIO17 ────────────────────┘──► UNO D10（F/L/R/Z/S/X）
              GPIO16 ◄────────────────────── UNO D11（O:左前,正前,右前,正後）
              GND 共地

邏輯電：3S 18650 → DC → XY3606（≈5.1V）→ USB-C → Pi 5
馬達電：獨立電池 → BMP73T104（勿灌 UNO 5V）；兩電池只共地
VL53×4：【已停用】舊腳位 XSHUT D2～D5；見 DEPLOY 附錄
```

注意：

- 拔掉錯誤接到 Pi 腳位直接當馬達 UART 的杜邦線（若曾試驗過）。
- D11→GPIO16 可留；目前不送 O:／網頁無 ToF。

### 6.3 馬達命令語意（UNO Pi-slave）

| 字元 | 意義 |
|------|------|
| `F` | Forward |
| `L` / `R` | 左／右轉（對準） |
| `Z` | 搜尋自轉 |
| `S` | Stop |
| `X` | Emergency stop（跌倒確認） |

## 八、端到端情境（可當演示腳本）

### 情境 A：安全跟隨

1. 開啟網頁預覽，確認骨架與距離數字有更新。
2. 開啟「跟隨」。
3. 人站畫面一側 → 車先轉向對準。
4. 人置中且距離 > 2 m → 前進；靠近 < 1.8 m → 停下。
5. 人離開畫面 → 自轉搜尋。

### 情境 B：跌倒通報與急停

1. 開啟「跌倒偵測」（可同時開或關跟隨）。
2. 模擬蹲下／半倒（非桌前打字坐姿），維持約 10 秒。
3. 預期：LINE 收到文字＋照片（＋可能影片）；若跟隨開著，馬達應 `X` 急停並可自動關跟隨。
4. 對照：坐在桌前打字不應進入確認警報。

### 情境 C：假警報自清

1. 短暫蹲下後立刻站起（未滿 10 秒）。
2. 預期：pending 被刪，不發 LINE。

## 九、風險、限制與未來工作

### 9.1 已知限制

- 單相機視野外無法視覺跟隨；依賴 `Z` 搜尋。
- 光線、遮擋仍影響追蹤；HSV Re-ID 在相似衣著多人時可能誤綁。
- UWB 受環境影響；stale 機制寧可停。（ToF／VL53 已停用）
- SoftSerial 雙向需額外接 **UNO D11→ESP32 GPIO16**。
- 圖床第三方服務可能間歇失敗；備援鏈降低但無法保證 100%。
- 非醫療認證；展示與課程用途為主。

### 9.2 未來可延伸（報告「展望」）

1. **MaUWB AOA**：角度 + 距離，弱光／背對相機時仍可粗跟隨。
2. **更強 Re-ID**（深度特徵／穿戴 Tag 綁定）。
3. **本地語音／蜂鳴器**雙通道警報（不只 LINE）。
4. **資料集微調**跌倒姿態，降低對通用 COCO 關鍵點規則的依賴。
